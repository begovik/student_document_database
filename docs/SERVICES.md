# Сервіси Harvester — огляд

> Головна ціль — збирати **якісні джерела з повним текстом**, придатні для наукових праць (титул, вступ/мета, розділи, висновки, список джерел). Не тези, не зміст, не анотації, не фрагменти.

Цей документ пояснює сервіси **людською мовою**: що це, що робить і як працює.
Інші джерела описів:

| Файл | Що там є |
|---|---|
| `docs/COMMANDS.md` | Перелік CLI-команд за сервісами з описом «що робить» для кожної команди |
| `docs/curator.md` | Детально про сервіс `curator`: етапи, структура JSON-каталогу |
| `docs/extraction.md` | Детально про `extract`: таблиця `extractions`, формат цитат/сумаризацій |
| `docs/TECHNICAL_DESIGN.md` | Технічна архітектура (SDD): потоки даних, схеми, діаграми компонентів |

## Швидка довідка

| Сервіс | Що робить (коротко) | Ключі / Моделі |
|---|---|---|
| `core/supervisor` + `core/scheduler` | Оркестрація 24/7, черга `tasks`, heartbeat | — |
| `discovery` (ddgs, openalex) | Пошук кандидатів, сідування `search_queries` | LLM-доповнення запитів: `GEMINI_API_KEY 1-3` |
| `verify` | Верифікація PDF (цілісність, `%PDF`, текстовий шар, мова, дедуп) | — |
| `classify` | Класифікація тем (УДК + ключові слова + LLM) | `GEMINI_DOC_VERIFIER_KEY_1..4`, `gemma-4-31b-it` / `gemma-4-26b-a4b-it` |
| `extract` | Витяг цитат і сумаризацій з PDF | `GEMINI_API_KEY 1..3`, `gemini-3.1-flash-lite` / `gemini-3.5-flash-lite` → fallback `gemma` |
| `curator` | Підготовка / верифікація каталогів | `GEMINI_API_KEY 1..3` (LLM-відбір) |
| `bibliography` | Витяг літератури з PDF та добирання джерел | `GEMINI_API_KEY 1..3` (спільний `LLMClient`), пошук `ddgs` |
| `verifier` | 24/7 повторна перевірка `verified` за `strict` | `GEMINI_DOC_VERIFIER_KEY_1..4`, `gemini-3.1-flash-lite` |
| `net` | HTTP-клієнт, anti-SSRF, blacklist, rate-limit | — |
| `db` | Failover `PostgreSQL ↔ SQLite`, міграції, репозиторії | `HARVESTER_PG_PASSWORD` |

## 1. Оркестратор: `core/supervisor` + `core/scheduler`

**Що це?** «Мозок» системи, що тримає її живою 24/7.

**Що робить?**
- Запускає всі воркери (пошук, верифікація, класифікація) і підтримує їхню роботу.
- Тримає чергу завдань у таблиці `tasks` — єдине місце, звідки воркери беруть роботу.
- Раз на кілька секунд записує heartbeat (ознаку, що сервіс живий), відслідковує та відновлює «застряглі» завдання (якщо воркер впав, його завдання повертаються у чергу через 30 с).

**Як працює?**
1. При старті: ініціалізує БД, наповнює таксономію тем, пошукові запити, чорний список.
2. Розкладає «рольові» завдання: одні воркери шукають, інші перевіряють PDF, треті класифікують.
3. Кожен воркер атомарно «забирає» завдання (`UPDATE ... WHERE status='pending'`), виконує, позначає результат.
4. При зупинці — коректно гасить воркерів і закриває БД.

## 2. Discovery: `discovery/ddgs_search` + `discovery/openalex`

**Що це?** «Пошуковик системи» — активні канали, які знаходять нові документи в інтернеті.

**Що робить?**
- DDGS: генерує пошукові запити та збирає посилання з пошукової видачі (DuckDuckGo).
- OpenAlex: тягне метадані наукових журналів через API OpenAlex.
- Класифікує знайдені посилання на «кандидатів» — готових піти на перевірку.

**Як працює?**
1. Бере завдання з черги (пошуковий запит) і виконує пошук по каналу.
2. Кожен знайдений URL перевіряється: чи дозволений домен, чи не в чорному списку, чи це PDF/наукова сторінка.
3. Унікальні кандидати вносяться в БД як документи зі статусом `discovered` → далі їх підхоплює верифікація.
4. Канали працюють з повагою до лімітів: глобальний семафор, на-доменні обмеження.

> Наразі реально ввімкнені лише `ddgs` і `openalex`. Crossref, Unpaywall, arXiv тощо — зарезервовані (`enabled: false`) до появи адаптерів.

## 3. Верифікація PDF: `verify/pipeline`

**Що це?** «Перевірщик» — вирішує, чи документ справді є придатним науковим PDF.

**Що робить?**
- Вантажить PDF, перевіряє що це справжній PDF (`%PDF`, розмір, magic bytes).
- Розпізнає текст, перевіряє наявність текстового шару, кількість сторінок.
- Визначає мову, тип документу, дедуплікує (за URL, SHA-256, DOI, схожістю назв).
- Відсіює російські/радянські джерела за правилами фільтрації.

**Як працює?** Покроковий ланцюжок `verify_document`:
1. `precheck` — дозволений URL? (блєкліст, анти-SSRF)
2. `HEAD`-запит — чи є PDF, які заголовки.
3. Завантаження файлу (у тимчасову теку, у серверному temp).
4. Парсинг: `%PDF`, текстовий шар, кількість сторінок, УДК, рік.
5. Фільтри: мова, довжина тексту, російська фільтрація.
6. Дедуплікація.
7. Рішення: `verified` (успіх) або код помилки (`not_pdf`, `too_small`, `blacklisted`, `filtered_ru`, …).
8. Кожна спроба логується в `fetch_attempts`.

> PDF зберігається **лише тимчасово** для перевірки; у БД лишаються тільки метадані, URL і SHA-256.

## 4. Класифікація: `classify/`

**Що це?** «Бібліотекар» — визначає, до яких тем належить документ.

**Що робить?**
- Прив'язує документ до тем і дисциплін (УДК, ключові слова, LLM).
- Формує таблицю `document_topics` — зв'язок «документ → тема».
- Допомагає далі шукати документи «за темою» або будувати каталог.

**Як працює?** Триетапно:
1. За УДК (якщо є) — зіставляє з префіксами тем.
2. За ключовими словами в назві/тексті.
3. LLM-верифікація (ModelRateLimiter, ротація ключів) для складних випадків — визначає найточнішу тему.
4. Складає бал (score) для кожної теми; документ отримує основну + додаткові теми.

## 5. Витяг цитат і сумаризацій: `extract/`

**Що це?** «Аналітик» — читає документ і пише, які цінні думки в ньому є та про що він.

**Що робить?**
- Для обраного документа бере PDF (локальний із каталогу або тимчасово завантажує), витягує текст.
- Викликає LLM, щоб знайти **цитати** (визначення, висновки, факти, методи) і скласти **сумаризацію** по розділах.
- Зберігає результат у таблицю `extractions` (JSON: `quotations`, `summary`).

**Як працює?**
1. Вибирає набір документів (за темою/каталогом/списком ID) через CLI `extract run`.
2. Вантажить/бере PDF, парсить текст (до ліміту сторінок і символів).
3. LLM-виклик із системним промптом → повертає `{"quotations":[...], "summary":{...}}`.
4. Нормалізує формат сумаризації (за замовчуванням — розділи).
5. Зберігає в БД; повторний запуск тих самих документів пропускає вже оброблені (`--skip-extracted`).

> Детальний формат цитат і сумаризацій — у `docs/extraction.md`.

## 6. Куратор каталогів: `curator/`

**Що це?** «Упорядник бібліотеки» — збирає та перевіряє тематичні каталоги готових джерел.

**Що робить?**
- `curator prepare TOPIC` — знаходить у БД найкращі документи за темою, перевіряє доступність і записує JSON-каталог у `catalogs/`.
- `curator verify CATALOG` — перевіряє готовий каталог: чи всі джерела доступні, виправляє помилки (заміна недоступних на схожі).

**Як працює (prepare)?**
1. Знаходить тему у таксономії або визначає УДК-префікси.
2. Збирає кандидатів: `verified`, повні метадані, `page_count >= 3`, текстовий шар.
3. LLM обирає оптимальну кількість (від `min_count` / `--limit`) і **найкращі цілісні** документи — відсіює тези, анотації, фрагменти.
4. Перевіряє доступність кожного обраного PDF (HEAD, таймаут).
5. Недоступні замінює на схожі з тієї ж теми.
6. Тимчасово завантажує кожен PDF для перевірки, записує JSON-каталог (тільки метадані + URL + SHA-256; PDF — тимчасовий).

**Як працює (verify)?**
1. Відкриває каталог, знаходить позиції з помилками.
2. LLM вирішує: `replace` (заміна) / `retry` (повтор) / `skip` (пропуск).
3. Виконує рішення, записує оновлений каталог `*_fixed.json`.

> Найкращі документи для каталогу — «цілісні джерела»: титул, вступ/мета, розділи, висновки, список джерел. Див. `docs/curator.md`.

## 7. Бібліографія: `bibliography/`

**Що це?** «Референс-менеджер» — дістає список літератури з документів і добирає саму літературу.

**Що робить?**
- Читає PDF з каталогу (або тимчасово вантажить), витягує блок «ЛІТЕРАТУРА/REFERENCES».
- Складає список літератури як текстовий файл.
- Для кожного посилання шукає, чи вже є цей документ у БД, а якщо ні — шукає в інтернеті (ddgs), перевіряє і реєструє.
- Відсіює російські посилання, дедуплікує.

**Як працює?** (`bibliography scan CATALOG_DIR`)
1. Для кожного документа каталогу: завантажити/взяти PDF → витягти текс, витягти REFERENCES (LLM + fallback regex).
2. Нормалізувати посилання (URL, DOI), відсіяти RU, прибрати дублі.
3. Кожне посилання: перевірити в БД; якщо нема — пошук в інтернеті, перевірка доступності, реєстрація у БД.
4. Результати — у `bibliography_*.json` + `*.txt`; тимчасові PDF видаляються.

## 8. Цілодобова перевірка: `verifier/`

**Що це?** «Аудитор» — фоново перевіряє вже `verified` документи на відповідність суворому профілю якості.

**Що робить?**
- Періодично (батч 20) перевіряє документи, які давно не перевірялись (`verifier_checked_at` старіше 7 днів або ще не перевірені).
- Застосовує швидкі правила без LLM (`page_count >= 3`, щільність тексту, RU-фільтр).
- Якщо треба — залучає LLM (ротація `GEMINI_DOC_VERIFIER_KEY_1..4`) для глибшої перевірки структури.
- Записує `verifier_results` (pass/fail + коментар строкою) і оновлює `documents.verifier_*`.

**Як працює?**
1. Вибрати наступний батч (тих, що не перевірені або перевірені давно).
2. Швидкі правила → якщо `fail` одразу; інакше RU-фільтр.
3. LLM-верифікація → `pass`/`fail` з коментарем про структуру («повна структура: титул, 12 стор., є вступ…»).
4. При вичерпанні всіх ключів на день — сон до півночі UTC.

> Детальніше — у `docs/COMMANDS.md#5`.

**Моніторинг та статистика:**
- `harvester report` — зведений звіт: стан системи, підсумок verifier і **поденна динаміка** перевірок (перевірено/pass/fail/LLM-виклики/перший-останній час LLM) за заданий період (дефолт 7 днів). Є `--json`.
- `harvester report --json | jq '.verifier.daily'` — ті самі дані у JSON.

**Зміст поденної динаміки** (з `verifier_results`, профіль `strict`):
| Дата | Перевірено | Pass | Fail | LLM-виклики | Перший LLM | Останній LLM |
|---|---|---|---|---|---|---|
| 09-04 | 17 780 | 11 487 | 6 293 | 2 263 | 06:06 | 13:00 |
| 09-08 | 12 000+ | ~6 200 | ~5 900 | ~1 900 | 09:25 | до вичерпання |

- Низька кількість `LLM-викликів` на день означає, що денні ліміти Gemini (`gemini_rpd=500` × `gemini_keys` + `classify_keys`, сумарно ~2000 запитів/день) вичерпуються класифікацією і verifier не встигає працювати.

## 9. Мережа: `net/`

**Що це?** «Поштовх» — єдиний спосіб, яким система виходить в інтернет (HTTP/2).

**Що робить?**
- Один HTTP-клієнт (httpx, HTTP/2) для всіх каналів і перевірки PDF.
- **Anti-SSRF**: забороняє звернення до приватних/внутрішніх адрес.
- **Чорний список доменів**: `.ru`, `.su`, `.рф` та інші — блокування.
- **Rate-limit**: глобальний семафор (32), на-доменні token buckets, ліміт пропускної здатності.
- Ручна обробка редиректів із перевіркою кожного нового URL.

**Як працює?**
1. Будь-який запит спершу проходить перевірку `is_url_allowed` (блєкліст + приватні IP).
2. Очікує своєї черги у лімітерах.
3. Редиректи йдуть поштучно з перевіркою кожного наступного URL (без авто-`follow_redirects`).
4. Повертає відповідь/PDF-байти того, хто попросив.

## 10. База даних: `db/`

**Що це?** «Сейф» — сховище даних із захистом від відмови.

**Що робить?**
- Головне сховище — **PostgreSQL**; локальна **SQLite** — резерв-дзеркало.
- У working-режимі кожен запис дублюється в обидві БД (дзеркало). Якщо PG недоступна — робота йде на SQLite, а зміни копляться в outbox і переграються в PG пізніше.
- Міграції схеми (нумеровані SQL-скрипти), репозиторії (зручні API над БД), переклад SQL-діалектів (`?` → `$N`, `ON CONFLICT`).

**Як працює?**
1. При старті `initialize()`: підключення до PG; якщо є зміни outbox — спершу їх виконує у PG.
2. Кожен DML (вставка/оновлення) виконується на активній БД та дублюється на іншу з тими самими id.
3. Якщо PG впала — перемикання на local; restore-probe періодично пробує повернутись і після успіху зливає накопичене.
4. CLI може відкривати БД **read-only** (звіти: `status`, `stats`, `db-size`) — без міграцій і записів у локальну копію.

## Спільний код (перевикористання)

- **Правила якості** — `harvester/config/rules.yaml` (строгі профілі) → `FilterRules` → `is_document_complete` (`curator/preparer.py`) → `analyze_pdf_quality` (`extract/pdf_quality.py`) → `verifier/rules.py`.
- **Пошук/завантаження** — `HttpClient` (`net/client.py`) + `ddgs_search` (`discovery/ddgs_search.py:18`).
- **LLM** — `LLMClient` (`classify/llm.py:87`) + `ModelRateLimiter` (`classify/ratelimit.py`) — єдина обгортка для Gemini/Gemma/OpenRouter, перевикористовується всіма LLM-сервісами (classify, extract, curator, verifier, bibliography).
