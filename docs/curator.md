# Сервіс curator — підготовка та верифікація каталогів документів

## Призначення

Сервіс `harvester/curator/` замінює `catalog_generator.py` і забезпечує:

1. **Підготовка каталогу** (`harvester curator prepare`) — відбір документів за темою, перевірка доступності, запис у унікальний JSON-файл
2. **Верифікація каталогу** (`harvester curator verify`) — перевірка існуючого каталогу, виправлення помилок через заміну недоступних джерел

## Встановлення

Сервіс вже інтегрований як підкоманда `harvester curator`. Додаткових дій не потрібно — просто переконайтеся, що LLM-конфігурація (Gemini API-ключі) налаштована.

## CLI-команди

### Етап 1: Підготовка каталогу

```bash
# Підготувати каталог для теми (LLM обирає кількість і найкращі документи)
harvester curator prepare "Підприємництво, торгівля та біржова діяльність"

# Обмежити кількість документів (опціонально)
harvester curator prepare "Економіка" --limit 50

# Dry-run: показати що було б зроблено, без запису файлу
harvester curator prepare "Інформатика" --dry-run
```

**Що робить:**
1. Знаходить тему в таксономії (або визначає UDC-префікси для нестандартних назв)
2. Збирає кандидатів з БД: `status=verified`, повні метадані, текстовий шар, **кількість сторінок не менше 3** (`page_count >= 3`) та відповідність вимогам щільності тексту
3. LLM обирає оптимальну кількість (20-50) і найкращі цілісні структуровані документи (промпт вимагає відсіювання 1-2 сторінкових тез, анотацій, чернеток та витягів)
4. Перевіряє доступність кожного обраного PDF (HTTP HEAD, таймаут 15с)
5. Замінює недоступні на схожі (з БД, та ж тема)
6. Завантажує відповідні PDF-файли у підпапку `resources/` та записує JSON-каталог: `catalogs/catalog_YYYYMMDD_HHMMSS/`

### Етап 2: Верифікація каталогу

```bash
# Перевірити і виправити помилки в каталозі
harvester curator verify catalogs/catalog_076.json

# Dry-run: показати план виправлення без змін
harvester curator verify catalogs/catalog_076.json --dry-run
```

**Що робить:**
1. Завантажує каталог, знаходить елементи з ключем `error`
2. Для кожного — LLM вирішує: `replace` (заміна), `retry` (повтор), `skip` (пропуск)
3. Виконує вирішення:
   - `replace` → шукає заміну в БД, перевіряє доступність, замінює в каталозі
   - `skip` → залишає помилку
4. Записує оновлений каталог: `catalogs/catalog_*_fixed.json`

## Перевірка доступності

Сервіс виконує HTTP HEAD-запит до `canonical_url` перед включенням документа в каталог:
- Таймаут: 15 секунд (5с connect, 5с read)
- Перевірка Content-Type (має містити "pdf" або "octet-stream")
- Якщо недоступно → позначається в БД (`documents.extra.curator`) і шукається заміна

## Заміна недоступних джерел

Коли джерело недоступне:
1. Сервіс шукає заміну серед наявних в БД:
   - `status = 'verified'`
   - Повні метадані
   - Не використані в каталозі
   - Та ж тема (document_topics) або UDC
2. Якщо заміна знайдена і доступна → використовується
3. Якщо заміна недоступна або не знайдена → оригінал позначається в БД

Маркування в БД (таблиця `documents`, колонка `extra`):
```json
{
  "curator": {
    "unavailable_since": "2026-08-22T20:18:43",
    "reason": "connect_timeout",
    "replaced_by": 54757,
    "catalog": "catalog_20260822_201843.json"
  }
}
```

## LLM-відбір документів

LLM отримує список кандидатів з метаданими і вирішує:
- Оптимальна кількість (20-50)
- Які документи обрати (релевантність + якість + різноманітність)
- Уникати: дублікати, документи з поганою якістю метаданих

Промпт містить інструкції щодо фільтрації поганих документів.

## Обмеження

1. **LLM-залежність**: якщо LLM недоступний, використовується запасний варіант (перші N документів)
2. **Якість метаданих**: сервіс залежиться від якості даних у БД. Документи з порожніми назвами, garbage-авторами можуть потрапити в каталог
3. **Доступність**: перевірка лише HTTP HEAD. Для деяких серверів HEAD може не працювати (відповідь 405). У такому разі використовується тільки статус-код.
4. **Заміна**: лише з наявних в БД. Якщо підходящої заміни немає, документ позначається і пропускається.

## Конфігурація

Сервіс використовує налаштування з `LLMConfig`:
- `enabled` — чи використовувати LLM для відбору
- `gemini_models` — моделі для класифікації
- `temperature` — температура LLM
- `max_tokens` — ліміт токенів
- `min_interval_s` — мінімальний інтервал між викликами
